# 交互式实验图

交互式实验图不是“会动的图”。它让读者改变一个受控输入，观察一个可解释的结果，从而回答静态图和固定动图回答不了的问题。ClickHouse 博客中的一些分阶段图值得借鉴的不是 GIF 文件格式，而是稳定的画布、逐步变化的状态，以及始终围绕同一机制推进的叙事。

本 skill 是 `blog-writing` 的图形式补充，不替代选题质量门、证据规则和图片规则。开始设计前，同时遵守 `review-rules/evidence.md`、`review-rules/image.md` 和 `review-rules/single-conclusion.md`。

## 先判断是否真的需要交互

先写出读者要回答的问题，再选择形式：

| 读者的问题                           | 首选形式                         | 是否交互   |
| ------------------------------------ | -------------------------------- | ---------- |
| 接下来发生了什么，顺序是什么？       | 带标注的分步图、静态序列或短动画 | 通常不需要 |
| 两种方案谁更大、差多少？             | 静态图、表或小多图               | 不需要     |
| 参数改变后，结果方向或量级如何变化？ | 可调参数的实验图                 | 需要       |
| 阈值、拐点或失效边界在哪里？         | 带基线、刻度和区间标注的交互图   | 需要       |
| 多个因素共同作用，结论不直观？       | 固定预设 + 单主变量交互          | 必要时使用 |

如果静态图已经能在一眼内完成比较，就不要做交互。如果过程完全固定，读者只能观看而不能提出问题，使用分步图或短动画即可。只有“读者需要测试自己的反事实”时，交互才提供信息增量。

### 参考 ClickHouse 的动图模式

ClickHouse 的[数据结构演进](https://clickhouse.com/blog/evolution-of-data-structures-in-yandexmetrica)使用分阶段图示说明数据布局如何变化。可迁移的模式是：

- 固定对象的位置和含义，只改变当前阶段真正变化的状态；
- 每次只解释一个机制，不靠镜头切换掩盖逻辑跳跃；
- 让读者先看见“前后差异”，再看到原因和代价；
- 动画不是装饰，它承担“状态如何演变”的论证。

不要复制视觉皮肤，也不要让效果比实验本身更抢眼。

## 交互实验图的设计合同

在画图或写组件前，先填完这张卡片。任何一项无法回答，都还没有到实现阶段：

```text
读者问题：
可调变量 X：
结果 Y：
基线：
X 的范围和步长：
证据类型：实测 / 解析模型 / 模拟
主结论：
失效边界：
不看动画也能得到的结论：
```

约束如下：

- **一个图只回答一个问题。** 如果可变参数同时改变多个互不相关的结论，拆成多个图或固定预设。
- **一个主变量。** 默认只暴露最能改变判断的旋钮；其他参数保持不变，或用少量命名预设表达。
- **结果可度量。** Y 必须有单位、方向、精度和比较基线；“看起来更快”不是结果。
- **模型先于界面。** 先把状态转移写成确定性函数或可复核的数据表，再决定颜色、动画和控件。
- **图必须能脱离动画阅读。** 初始或默认状态应直接给出最终结果、关键数值和结论；播放只是补充过程。

## 证据边界

图中每个数字都要能追溯到来源，且必须区分：

- **实测结果**：数据、代码版本、运行环境、参数、重复次数和原始结果位置；
- **解析模型**：公式、输入范围、假设和单位；
- **模拟或教学模型**：哪些是真实的，哪些是为解释而压缩的可视化。

不要把模型输出写成实测结果。例如，查找比较次数可以由算法精确计算，但“磁盘延迟”不能由比较次数直接推出。图中压缩了大量原始步骤时，要明确写出“视觉进度已压缩，数字仍为精确值”。

如果参数只覆盖很小或人为挑选的范围，说明范围如何选取。不要用单点演示暗示普遍规律。

## 状态和视觉设计

### 状态序列

1. 先定义起始状态、关键转折点和结束状态，再决定帧数。
2. 只保留能改变读者判断的状态。不要为每一次低层操作都做一帧；把重复操作聚合，并说明聚合规则。
3. 有时间序列时，默认展示结束状态；播放时从起点重新开始，允许暂停、单步、重置和拖动时间轴。只有参数变化的图不需要伪造时间轴。
4. 状态变化时保持布局、坐标范围、图例和标签位置稳定。读者不应在每一步重新学习画面。
5. 对比两个方案时，把可比较的量放在同一尺度、同一方向和对齐的轨道上。

### 视觉编码

- 用一个强调色表示当前动作或当前状态，其余元素降低视觉权重。
- 不要只用颜色区分状态；同时使用位置、形状、文字或标记。
- 直接标注关键差异，少用需要来回查找的图例。
- 去掉装饰性背景、无信息动画和重复标签。
- 图中可见嵌套最多三层；超过时平铺对象或拆图。
- 移动端优先减少刻度、缩短标签或拆图，不要缩小文字来塞入更多信息。

## 交互与可读性

- 不自动播放。自动播放的 GIF 既无法暂停，也无法让读者测试自己的假设。
- 控件随形式选择。时间序列图提供播放/暂停、单步、重置和时间轴；参数图提供默认值和重置。不要为了形式统一添加无意义的播放按钮。
- 所有控件都要能用键盘操作，并显示当前值。
- 提供当前状态的可读文本摘要，例如“第 4 帧，顺序扫描 73 次比较，二分查找 4 次比较”。
- 遵守 `prefers-reduced-motion`：减少过渡，不删除信息。
- 颜色、图例和文字在浅色、深色和窄屏下都要可读。
- 如果动画超过约 5 秒或状态超过约 20 个，先问它是否应该拆成多个阶段或改成静态小多图。
- 移动端控件不能被折叠到图下方而失去上下文；图、控件、结果和说明应在同一阅读单元内。

## 写作中的位置

交互图前后都要有正文论证，不能把图当作独立文章：

1. **图前**：说明读者要比较什么、参数代表什么、范围为什么这样选，以及应该观察哪个结果。
2. **图后**：报告读者应看到的结论、关键边界和不能从图中推出的内容。
3. **图注**：补充比较条件、数据范围、模型与实测的区别、聚合规则或需要记住的限制；不要只重复标题。

图只支持文章的主结论，不要在图后引入第二个独立结论。如果图展示的是一个意外现象，先说明它如何限定或修正主结论。

## 推荐工作流

1. **完成设计合同。** 把问题、X、Y、基线、范围、证据类型和失效边界写成一句话。
2. **过形式选择门。** 静态图或固定分步图够用时，停止，不引入交互。
3. **建立确定性模型。** 把计算、状态和渲染分开；为最小值、最大值、相等、未命中和非法输入写测试。
4. **挑选有意义的状态。** 默认显示最终状态，保留能解释机制的 8–20 个阶段；压缩重复步骤并写明。
5. **设计控件和降级。** 一个主变量、重置、键盘操作和无动画摘要；有时间序列时再加播放/暂停、单步和时间轴。
6. **检查阅读路径。** 遮住动画，只看默认画面，读者能否说出主结论、比较条件和边界？不能则重做。
7. **验证。** 检查浅色/深色、390px 窄屏、桌面、键盘、减少动态效果和最终静态状态；模型另做确定性测试。
8. **回填图注和正文。** 写清实测/模型、范围、压缩规则和限制，再让图进入文章。

## 失败模式

出现以下任一情况，优先删掉交互或退回静态图：

- 动画只是让页面“更高级”，删掉后论点不变；
- 控件很多，但没有一个能改变技术判断；
- 读者必须从头看完动画，才能知道结论；
- 结果没有基线，或者坐标轴随参数变化；
- 只展示有利区间，隐藏阈值或失败状态；
- 把模型输出、模拟结果或教学压缩写成实测数据；
- 依赖颜色、悬停或鼠标才能理解；
- 一张图同时讲算法、性能和成本三个独立结论。

## 交付前自检

- [ ] 读者能用一句话说出这张图回答的问题。
- [ ] 只有一个主变量，且它确实改变结论或边界。
- [ ] 图在不动画时仍能读出结果、单位和比较基线。
- [ ] 实测、解析模型和模拟的边界已写在图注或正文。
- [ ] 状态数量、播放时长和压缩规则合理。
- [ ] 时间序列图有播放/暂停、单步、重置和时间轴；参数图有默认值和重置。
- [ ] 所有控件可用键盘操作，减少动态效果时信息不丢失。
- [ ] 浅色、深色、窄屏和图内字号已验证。
- [ ] 图后结论没有超出图和数据能支持的范围。

如果第 1、2、3 或第 8 项不通过，不要交付。交互复杂度不能弥补论证缺口。
